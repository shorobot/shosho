# DECISIONS — архітектурні рішення SHOSHO

Формат: `D-NNN — назва` / Статус / Рішення / Чому / Наслідки. Рішення не переписуються — якщо змінюється, додається нове з посиланням на старе.

---

## D-001 — Технологічний стек
Статус: прийнято (2026-09-17, власник + Orchestrator)
Рішення:
- БД / auth / realtime: **Supabase** (Postgres, Row Level Security, Realtime)
- Гостьовий сайт + замовлення + бек-офіс: **Next.js** (App Router, TypeScript)
- AI-агенти: **Claude Agent SDK**
- Оркестрація агентів / інтеграції: **n8n**
- Зовнішні інтеграції (Lieferando / Wolt): **FastAPI** endpoint
Чому: realtime з коробки для операторського екрану; один Postgres для всіх шарів; агенти працюють поверх тієї ж БД без окремої шини.
Наслідки: усі сесії пишуть у ту саму схему Supabase; контракти між шарами = таблиці + RLS + REST/RPC, документуються в /docs/api-contracts.md.

## D-002 — Пам'ять проєкту живе в git
Статус: прийнято (2026-09-17)
Рішення: `/memory` у головному репозиторії — єдине джерело правди про стан. Кожна сесія читає state.md + decisions.md перед стартом, пише в log.md після.
Чому: контекст сесій Claude обривається; файли в git — ні.
Наслідки: кожен коміт з префіксом `[<сесія>-<boot>]`. Orchestrator — єдиний, хто редагує decisions.md і таблицю state.md цілком; дочірні сесії — тільки свій рядок і log.md.

## D-003 — Послідовний старт, один активний boot на напрямок
Статус: прийнято (2026-09-17)
Рішення: DevOps → Backend → Frontend → Back-office, далі Automation ‖ QA ‖ Security паралельно. На кожен напрямок — не більше одного відкритого boot одночасно.
Чому: кожен шар залежить від контрактів попереднього; паралельні зміни одного контракту без координації ламають систему.
Наслідки: зміна спільного контракту (API, схема БД) — тільки через Orchestrator, який оновлює /docs/api-contracts.md і видає boot обом сторонам.

## D-004 — Хостинг / сервер
Статус: **ВІДКРИТО** — вирішує DevOps-01 разом із власником
Варіанти: (a) власний VPS (Hetzner / існуючий сервер власника) + Docker Compose; (b) Vercel для Next.js + Supabase Cloud + окремий VPS для n8n/FastAPI.
Критерії: вартість, наявність існуючого сервера, GDPR (дані в ЄС), простота CI/CD.

## D-005 — Середовища
Статус: прийнято (2026-09-17)
Рішення: два середовища — `staging` (гілка `main`, автодеплой) і `prod` (git tag `v*`, ручний approve). Локальна розробка — `.env.local` + Supabase local або окремий dev-проєкт Supabase.
Чому: команда з AI-сесій робить багато дрібних комітів; prod не повинен ламатись від кожного.
Наслідки: DevOps-01 налаштовує обидва pipeline; Security перевіряє prod-деплой перед кожним тегом.
