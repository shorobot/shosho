## Tasks
1. **Stripe — schema** (migration): `orders.payment_provider text null` (`stripe` | null), `orders.payment_intent_id text null unique`, `orders.payment_captured_at`, `orders.payment_refunded_cents int default 0`; `payment_events` table (`id`, `order_id`, `provider`, `event_id text unique`, `type`, `payload jsonb`, `received_at`) for idempotent webhook processing. Enum `payment_status` stays (pending/authorized/paid/failed/refunded).
2. **Stripe — RPC** `create_payment_intent(order_id uuid)` → returns `{client_secret, publishable_key_name}`; security definer, callable by `anon` only when the caller presents the order's `tracking_token` (pass it as a parameter, verify it) and by staff. Creates a PaymentIntent `amount = total_cents`, `currency = eur`, `capture_method = manual`, `automatic_payment_methods` on (cards, Apple/Google Pay, PayPal), `metadata.order_id`, stores `payment_intent_id`, sets `payment_provider = stripe`. Uses `pg_net`/`http` extension to call Stripe? — **No**: keep secrets out of Postgres. Implement it as an **Edge Function** `create-payment-intent` (Deno, `STRIPE_SECRET_KEY` from function secrets) that validates the order via the service-role client and writes back. Expose the same contract to S3 as `supabase.functions.invoke('create-payment-intent', {body: {order_id, tracking_token}})`.
3. **Stripe — webhook** Edge Function `stripe-webhook`: verifies the signature (`STRIPE_WEBHOOK_SECRET`), records the event in `payment_events` (skip duplicates by `event_id`), maps: `payment_intent.amount_capturable_updated` → `payment_status = authorized` + `order_events(payment_authorized)`; `payment_intent.payment_failed` → `failed` + event; `payment_intent.succeeded` (after capture) → `paid` + `payment_captured_at`; `charge.refunded` → `refunded` / `payment_refunded_cents`. Auto-accept rule from S2-01 (`authorized` & ASAP & total < 50 € & kitchen not paused) must fire when authorization arrives via webhook, not only at `place_order`.
4. **Stripe — capture / void / refund on status change**: replace the v1 stub in `set_order_status`. `delivered` / `picked_up` with `payment_provider = stripe` → enqueue a capture; `cancelled` → void (cancel the PaymentIntent); `refunded` → refund (full, or `payload.amount_cents` partial). Because Postgres must not hold the Stripe key, do this as: `set_order_status` inserts a row into `payment_jobs(id, order_id, action capture|void|refund, amount_cents, status queued|done|failed, attempts, last_error)` and an Edge Function `payment-worker` processes queued jobs (invoked by a `pg_cron` schedule every minute if available on the plan, otherwise by a Supabase scheduled function / cron trigger — document which). Cash: `set_order_status(delivered, {cash_received: true})` sets `paid` directly, `{cash_received: false}` leaves `pending` and writes a `note` event.
5. **Storage**: bucket `menu` (public read; insert/update/delete for `owner`/`operator` via storage policies); `menu_items.photos` paths are `menu/<item_id>/<n>.jpg`. Migration for bucket + policies. Document the upload path for S4 (`storage.from('menu').upload`). Optional: bucket `receipts` (private) reserved for later — skip unless trivial.
6. **Operator order edits** RPC `update_order_items(order_id, items jsonb)` — staff (operator/owner) only, allowed while status ∈ {new, accepted, preparing}: replaces `order_items` with the given list (same item shape as `quote_order`), re-quotes server-side with the order's type/zone/promo, updates totals, marks changed rows `modified_by_operator`, writes `order_events(item_changed, payload = diff)`. If a Stripe intent exists and is `authorized`, update the PaymentIntent amount (via a `payment_jobs` action `update_amount`); if the new total exceeds the authorized amount by more than Stripe allows, reject with `amount_exceeds_authorization`.
7. **Customer timeline**: `customer_events` table per §1.3 (`type` order/complaint/compensation/note/push_opened/consent_changed; `payload`; `actor_id`); triggers: new order → `order` event; `set_order_status` `payload.note` → `note` event; RPC `add_customer_event(customer_id, type, payload)` for staff (complaint/compensation/note). Consent changes on `customers` → `consent_changed` event (trigger).
8. **Guest realtime** (§3): make the tracking page subscribable — simplest safe route: a view `order_tracking` (the same projection `get_order_by_token` returns) with RLS `tracking_token = current_setting('request.headers')::json->>'x-tracking-token'`; document for S3 how to set the header on the realtime client (`supabase.realtime.setAuth` is not it — use `headers` on the client + `postgres_changes` on `orders` filtered by `id`). If header-based RLS for realtime proves unworkable, keep polling and say so — do not spend more than a day on this.
9. **Anonymisation**: function `anonymise_silent_customers(months int default 24)` — for customers with no order in `months` and `anonymised_at is null`: scrub `name` → 'Anonymised', `phone` → `anon-<id>`, `email` → null, delete `customer_addresses`, keep orders/totals (GoBD), set `anonymised_at`, write `customer_events(anonymised)`. Schedule nightly 03:00 Europe/Berlin via `pg_cron` if the plan has it; otherwise document the manual/S5 cron path. Never run it in seed.
